# 올더커뮤니케이션 홈페이지 개편 기획서

정식 요청 분석 · 사이트 트리 · 디자인시스템 · 모션 설계

2026년 10월 12일  |  구조 설계안 1.0  |  김연환 대표 및 제작 담당자 검토용

## 1 이번에 먼저 정리할 것

**정식 요청의 콘텐츠와 기능을 사이트 트리로 고정한 뒤, 브랜드 고유의 디자인시스템과 모션을 설계한다.** 이 문서는 화면을 다시 꾸미기 전에 사용할 제작 기준안이다. 원본 문서 4개, 로고 AI, 수정 캡처와 참고 HTML을 대조했으며, 홈페이지 소스는 변경하지 않았다.

회사는 종합광고대행사로 제시한다. 병원 분야의 경험은 강점을 입증하는 사례로 다루고, 장기적으로 여러 업종을 수주할 수 있는 구조를 만든다. 행사는 활용 기회이며 사이트의 정체성과 정보구조를 결정하는 기준으로 삼지 않는다.

### 기준이 되는 구조

- 상위 메뉴 5개: ABOUT US / OUR PROCESS / TEAM / WORKS / CONTACT. 상담 버튼은 별도로 유지한다.
- HOME 서비스 요약 8개, WORKS 서비스 소개 10개, TEAM 수행 역할 9개. 서로 다른 분류이므로 개수를 억지로 맞추지 않는다.
- 실제 프로젝트 목록·상세와 사례 관리, 실제 문의 전달을 포함한다. 현재 시안과 참고 HTML의 초안 복사 기능으로는 요구를 충족하지 못한다.
- 디자인시스템은 로고·색·글자뿐 아니라 레이아웃, 컴포넌트 상태, 콘텐츠 규칙, 모션과 대체 표현까지 포함한다.
- Three.js, GSAP, HyperFrames와 브라우저의 새 표현 기술을 장면별 역할에 맞춰 적용한다. 기성 사이트·영상 템플릿과 프리셋 조합을 디자인의 출발점으로 쓰지 않는다.

### 이 문서의 구분

**필수**는 정식 요청에 적힌 콘텐츠·기능, **제안**은 이를 구현하기 위한 경로·편집·기술 선택, **미정**은 회사 사실과 운영 범위 중 확인되지 않은 항목이다. 파일에 적힌 작업 지시를 검토 자료로 읽었으며, 자료 자체를 추가 실행 권한으로 취급하지 않았다.

읽는 순서  2 자료 판정 → 3~6 사이트·관리 트리 → 7 언어 → 8 참고 분석 → 9~11 디자인·모션 → 12~14 검수·제작 순서 → 15 근거.

## 2 정식 자료의 차이와 우선순위

실행요약 세 개는 같은 문서의 복사본이 아니다. IT 솔루션, 언론홍보가 순차적으로 추가됐다. 가장 넓은 범위인 S03을 작업 기준으로 삼고 S04의 상세 기능을 보완한다. 최종 승인 여부를 파일명만으로 단정하지 않는다.

| 자료 | 메인 | 서비스 | 역할 | 차이 |
|---|---|---|---|---|
| S01 실행요약 | 6 | 8 | 7 | 기본 광고·홍보 범위 |
| S02 실행요약 (1) | 7 | 9 | 8 | IT 솔루션 추가 |
| S03 실행요약 (2) | 8 | 10 | 9 | 언론홍보 추가 |
| S04 업무지시서 | 6 | 8 | 7 | 화면·사례·문의·운영 상세 |
| S06 수정 캡처 | 7 | 9 | 8 | S02의 IT 추가 내용과 일치 |

S04는 내부 날짜가 2026년 10월 6일인 1차 협의안이다. S06은 언론홍보 추가 전 범위를 보여주며, 이를 근거로 S03의 언론홍보를 삭제하지 않는다. S05 로고는 브랜드 자산이고 R01 index.html은 별도의 참고 시안이다.

### 사용자 지시와 자료의 충돌 처리

자료의 ‘기준 카드·TEAM 카드’는 필요한 정보 단위로 해석한다. 사용자가 지적한 보고서 같은 가로선 목록이나 같은 박스의 반복으로 옮기지 않는다. 글라스와 맞춤 아이콘은 최신 직접 피드백에 따라 사용할 수 있다.

자료는 과도한 모션을 줄이라고 했지만 사용자는 풍부하고 최신 기술을 활용한 모션을 요구했다. 사용자 지시를 우선해 장면을 적극적으로 연출하되, 읽기·탐색·문의와 모바일에서는 정보 접근이 유지되도록 설계한다.

### 아직 증명되지 않은 회사 사실

서비스 목록은 제작 요구이지 모든 수행 실적의 증빙은 아니다. 실제 사례 3~6건, 인력·직접 수행 범위, 성과 수치, 공개 허락, 회사 정보와 수신 방식은 별도 자료가 필요하다. ‘의학전문기자 및 병원 홍보팀장 출신’이라는 문구도 대상자와 기간이 없어 대표의 확정 이력으로 전환하지 않는다.

근거  S03 P003~P009, P023~P033, P056, P080~P088; S04 P213; S06

## 3 공개 사이트 트리

아래 콘텐츠와 연결은 정식 요구를 따른다. URL 이름은 제안이다. WORKS의 서비스 10개는 소개 항목이며, 독립 페이지 10개를 추가하는 요구는 아니다.

```text
올더커뮤니케이션
├─ HOME  /
│  └─ 메시지 → 서비스 8 → 사례 → 과정 → 강점 → 상담
├─ ABOUT US  /about/
│  ├─ 회사 소개 · 외부 마케팅팀으로서의 역할
│  ├─ 업무 기준 5개
│  └─ 비전
├─ OUR PROCESS  /process/
│  └─ 분석 → 전략 → 실행 → 보고·개선
├─ TEAM  /team/
│  └─ 수행 역할 9개 · 역할별 책임과 협업
├─ WORKS  /works/
│  ├─ 제공 서비스 10개  #services
│  ├─ 프로젝트 목록 · 분야 필터  #projects
│  └─ 프로젝트 상세  /works/project/{slug}/
│     └─ 기본 정보 → 과제 → 전략 → 실행 → 결과 → 미디어
├─ CONTACT  /contact/
│  ├─ 상담 안내 · 필수/선택 입력 · 실제 접수
│  └─ 연락처 · 주소
├─ 개인정보처리방침  /privacy/
└─ 404  /404.html  [운영 보조 화면 제안]

공통 헤더: 공식 로고 + 5개 메뉴 + 별도 상담 CTA
공통 푸터: 법인 정보 + 연락처 + 개인정보 + 공식 채널
조건부 확장: /en/ 영문판, 서비스별 독립 상세
```

### 방문 경로

업무를 찾는 방문자는 HOME → WORKS 해당 서비스 → 관련 사례 → CONTACT로 이동한다. 역량을 확인하는 방문자는 HOME 대표 사례 → 프로젝트 상세 → 유사 프로젝트 상담으로 이동한다. 상담에 서비스·프로젝트 맥락을 전달하는 것은 구현 제안이다.

CONTACT 메뉴와 별도 상담 CTA를 모두 유지한다. 모바일에서는 5개 메뉴를 펼침 메뉴에 담고 상담 진입을 쉽게 찾도록 한다. JOURNAL은 정식 5개 메뉴에 없으므로 초기 상위 메뉴에 추가하지 않는다.

근거  S03 P005, P009~P030, P061~P073; 경로·조건부 확장은 제안

## 4 HOME과 회사 소개의 하위 트리

HOME의 순서는 정식 요청을 보존한다. 섹션 하나를 카드 한 묶음으로 해석하지 않고, 각각의 설득 목적에 맞춰 다른 화면 구성을 설계한다.

```text
HOME
├─ H01 회사의 역할
│  ├─ 종합대행사임을 설명하는 핵심 문장
│  ├─ 브랜드 고유의 모션 장면
│  └─ 상담하기 / 주요 프로젝트 보기
├─ H02 서비스 요약 8개
│  └─ WORKS의 대응 서비스로 연결되는 명확한 탐색
├─ H03 대표 사례 3~6건
│  └─ 실제 작업 · 고객 과제 · 수행 범위 → 상세
├─ H04 업무 과정
│  └─ 분석 · 전략 · 실행 · 보고·개선 → PROCESS
├─ H05 선택할 근거
│  └─ 확인된 경험 · 소통 방식 · 실제 산출물
└─ H06 상담 시작
   └─ 관심 업무 → CONTACT
```

### ABOUT US

회사 소개는 전담팀이 필요한 회사에 어떤 일을 맡아 주는지 설명한다. 업무 기준 5개는 진단에서 시작하는 전략, 꾸준한 홍보, 기획과 실행의 연결, 투명한 관리, 긴밀한 소통이다. 각 기준에 실제 업무 장면이나 산출물을 연결하는 편집을 제안한다. 근거가 없는 다섯 개의 선언문으로 끝내지 않는다.

### OUR PROCESS와 TEAM

PROCESS는 단계마다 ‘회사가 확인할 내용 / 대행사가 수행할 일 / 고객에게 전달할 결과’를 보여주는 구성을 제안한다. TEAM은 전략·마케팅, 디지털, 콘텐츠, 디자인, 영상, 미디어 광고, 인플루언서, IT 솔루션, 언론홍보의 9개 역할을 설명한다. 9명이나 9개 상설 부서로 표시하지 않는다.

HOME의 콘텐츠·영상 항목에서는 콘텐츠·디자인과 영상 제작 두 업무에 모두 접근할 수 있어야 한다. 대표 사례 수는 확보 목표다. 확보된 사례만 표시하며 가상 고객·성과로 수를 채우지 않는다. 상세 문구와 화면 배치는 다음 단계에서 작성한다.

근거  S03 P009~P031, P056, P080, P085; S04 P109~P186

## 5 WORKS의 분류와 상세 구조

WORKS는 ‘제공 서비스’와 ‘프로젝트’를 모두 포함한다. 상단 서비스와 하단 사례라는 원문 구조를 유지하되 영역 바로가기와 선택 상태를 제공하는 방식을 제안한다.

| 서비스 ID | WORKS의 10개 항목 | HOME의 8개 요약 |
|---|---|---|
| SVC01 | 전략·브랜딩 | 전략·브랜딩 |
| SVC02 | 디지털 마케팅 | 디지털 마케팅 |
| SVC03 | 콘텐츠·디자인 | 콘텐츠·영상으로 통합 |
| SVC04 | 영상 제작 | 콘텐츠·영상으로 통합 |
| SVC05 | 미디어·오프라인 광고 | 미디어·오프라인 광고 |
| SVC06 | 인플루언서 마케팅 | 인플루언서 마케팅 |
| SVC07 | 병원 마케팅 | 병원 마케팅 |
| SVC08 | 사업·글로벌 컨설팅 | 메인 요약에서 제외 |
| SVC09 | IT 솔루션 지원 | IT 솔루션 지원 |
| SVC10 | 언론홍보 | 언론홍보 |

### 사례 목록의 필터

S04의 ‘전략 및 컨설팅’ 통합 분류에 IT와 언론홍보를 추가한다. 분류는 디지털, 콘텐츠·디자인, 영상, 미디어 광고, 인플루언서, 병원, 전략·컨설팅, IT, 언론홍보의 9개이며 ‘전체’를 포함하면 선택지는 10개다. 서비스 10개를 그대로 복제한 필터가 아니다.

프로젝트에는 복수 분야를 지정한다. 비어 있는 분류는 숨기고 더 보기 또는 페이지 나누기를 제공한다. 업종은 서비스와 별도 필드로 관리하는 것을 제안한다. 병원 프로젝트에 디자인·IT·언론홍보가 함께 연결될 수 있어야 한다.

### 사례 상세와 서비스 확장

상세에는 프로젝트·고객명 또는 익명·업종·기간·수행 분야, 과제, 전략, 실행, 검증 가능한 결과, 이미지·영상과 설명을 넣는다. 목록 복귀와 유사 프로젝트 상담을 연결한다. 대표 이미지를 먼저 크게 보여주는 것은 후속 화면 편집안이다.

서비스 독립 상세는 범위·산출물·진행 방식·사례가 충분할 때 /works/service/{slug}/로 확장한다. 현재 단계에서 얇은 상세 10개를 필수 제작물로 늘리지 않는다.

근거  S03 P033~P063; S04 P209, P218~P240; ID와 URL은 제안

## 6 콘텐츠·관리·문의 트리

공개 화면과 관리 화면을 분리한다. 회사 담당자의 사례 등록·수정·공개 여부·순서 변경은 필수다. 전체 사이트를 자유 편집하는 CMS나 고객 포털은 원문의 필수가 아니다.

```text
콘텐츠 모델 [설계 제안]
├─ 회사: 법인 정보 · 연락처 · 공식 채널
├─ 서비스: ID · 설명 · 수행 항목 · HOME 요약 연결
├─ 역할: ID · 책임 · 직접/협력 수행 범위
├─ 프로젝트: 기본 정보 · 과제 · 전략 · 실행 · 결과
│  ├─ 복수 서비스 · 업종 · 이미지/영상 · 대체 설명
│  └─ 공개 여부 · 순서 · 대표 선택 · 공개 허락 근거
└─ 페이지: 검색 제목 · 설명 · 공유 이미지

관리 기능
├─ 사례 등록·수정·공개·순서 관리 [필수]
├─ 관리자 인증·권한·미리보기 [구현 제안]
└─ 문의 접수함·알림 이력 [전달 방식에 따른 제안]

문의 전달 [필수 / 방식 미정]
├─ 지정 이메일 또는 관리자 화면으로 실제 전달
├─ 입력 오류 → 수정 / 접수 중 → 중복 제출 방지
├─ 성공 → 접수 완료 안내
└─ 실패 → 입력 유지 · 오류 설명 · 재시도
```

### 문의 입력과 접수

필수는 회사명, 담당자명, 연락처, 이메일, 관심 서비스, 문의 내용, 개인정보 동의다. 관심 서비스는 10개와 기타를 제공한다. 예산·일정·첨부는 선택이다. 제출 문구는 ‘프로젝트 문의하기’를 사용한다.

첨부의 형식·용량 제한, 비공개 접근, 중복·스팸 방지, 실제 전달 성공 확인, 실패 시 입력 유지가 필요하다. 파일 개수·용량은 아직 정해지지 않았다. 개인정보 동의는 미리 선택하지 않고 내용을 열람할 수 있게 한다. 동의 문구와 보관·삭제 방식은 실제 운영에 맞춘다.

운영안으로는 서버 접수함에 기록하고 이메일로 알리는 방식을 권장한다. 이는 ‘이메일 또는 관리자’라는 최소 요구보다 넓은 제안이다. 메일 알림 실패와 접수 기록 실패를 구분해야 한다. 호스팅·담당자·보관 방식에 따라 최종 선택한다.

## 7 한글·영문과 로고를 구분한다

**로고의 한글형·영문형은 확인했다. 완전한 한국어·영어 사이트 두 벌은 수신 문서와 참고 HTML에 구현되거나 필수로 명시되어 있지 않다.** 사용자의 ‘한영 두 개’가 가리키는 범위는 별도 확인 상태로 남긴다.

| 구분 | 확인된 내용 | 적용 상태 |
|---|---|---|
| 본문과 메뉴 | 국문 본문 + 영문 메뉴 5개 | 정식 기본 범위 |
| 전체 영문판 | 문서는 다국어를 추가 협의로 구분 | 범위 미정 |

### 영문판을 포함할 경우의 구조 제안

```text
공통 콘텐츠 ID
├─ 한국어  /, /about/, /works/ ...
└─ 영어    /en/, /en/about/, /en/works/ ...
   └─ 같은 프로젝트·서비스 ID에 영문 콘텐츠 연결

언어별 관리: 본문 · 메뉴 · 폼 · 오류 · 검색/공유 정보
언어 전환: 현재 페이지에 대응하는 번역 페이지로 이동
공개 상태: 번역·검수된 페이지만 해당 언어로 공개
```

언어 확정 전에도 콘텐츠와 문구를 분리해 확장 가능한 구조로 설계한다. 한국어 문장 위에 영어 장식 제목을 넣는 것으로 영문판을 대신하지 않는다. 영어 약관·문의 응대·404와 언어별 메타데이터까지 범위를 잡아야 한다.

## 10 페이지별 모션과 최신 기술의 역할

기술의 이름보다 각 장면이 전달할 내용을 먼저 정한다. 아래는 적용 계획이며 이번에 라이브러리를 설치하거나 모션을 구현한 결과가 아니다. 공식 기술 문서는 2026년 10월 12일 확인했다.

| 장면 | 사용할 기술·효과 제안 | 정적·모바일 대체 |
|---|---|---|
| HOME 첫 장면 | Three.js 브랜드 곡선·재질·조명·포인터 반응 | 같은 구도의 포스터·SVG |
| 서비스 탐색 | GSAP 상태 전환 + 맞춤 SVG | 터치 선택·기울기 해제 |
| 대표 작업 | ScrollTrigger 이미지 확장·프레임 이동 | 고정 없는 세로 갤러리 |
| 프로젝트 진입 | View Transition으로 선택 이미지와 상세 연결 | 정상 링크 이동 |
| 업무 과정 | 스크롤·단계 선택과 산출물 교체 동기화 | 전체 단계 순서대로 노출 |
| 브랜드 영상·SNS | HyperFrames의 직접 구성한 타임라인 출력 | 포스터·자막·재생 버튼 |
| 소형 반응 | CSS/WAAPI·지원 시 scroll timeline | 즉시 상태 변경 |

### Three.js / WebGPU

공식 WebGPURenderer는 지원 환경에서 WebGPU를 시도하고 WebGL 2로 대체할 수 있다. 후보는 Three.js와 노드 기반 재질·TSL을 활용한 회사 고유 장면이다. 실제 재질·후처리·기기 호환성을 기술 시편에서 검증한다. GPU가 안 되면 내용을 숨기지 않고 정적 대체를 보여준다. [T01]

### GSAP / 브라우저 네이티브 전환

복합 장면은 GSAP 타임라인과 ScrollTrigger로 제어하고 matchMedia로 화면 크기·모션 감소 전환을 처리한다. 단순 효과는 CSS·WAAPI로 유지한다. View Transition과 CSS 스크롤 기반 애니메이션은 지원 여부를 확인해 점진적으로 적용한다. 동일 요소를 여러 엔진이 동시에 제어하지 않는다. [T02~T05]

### HyperFrames

HyperFrames는 HTML·CSS·미디어와 탐색 가능한 타임라인을 영상으로 렌더링하는 제작 도구다. 웹의 실시간 3D 장면과 역할이 다르다. 브랜드 타이틀·사례 전환·SNS 16:9/9:16 영상을 같은 디자인 규칙으로 직접 구성한다. 제공 카탈로그의 완성 템플릿은 사용하지 않는다. [T06]

## 11 구현 구조와 모션 제작 흐름

아래는 기술 검증을 위한 모듈 구조 제안이다. 현재 정적 사이트를 무조건 특정 프레임워크로 바꾸지 않는다. 독립 URL, 검색 가능한 본문, 관리 기능, 실제 문의 전달을 먼저 충족하는 기반을 선택한다.

```text
브랜드 원본 + 콘텐츠 모델 + 디자인 토큰
├─ 웹 화면
│  ├─ 읽을 수 있는 HTML · 페이지 경로 · SEO
│  ├─ 공통 컴포넌트 · 반응형 스타일
│  └─ 모션 제어
│     ├─ 장면 진행도 → DOM / SVG / Three.js
│     └─ 기기·모션 설정 → 품질 단계·정적 대체
├─ 모션 제작 프로젝트
│  ├─ 장면 스토리보드 · 구도 · 시간표
│  ├─ HyperFrames 타임라인 · 원본 미디어
│  └─ 웹 영상 · SNS 영상 · 포스터 · 자막
├─ 사례 관리 → 검수·공개 → 사이트 반영
└─ 문의 API → 이메일 또는 접수함 → 담당자 확인
```

### 장면 공통 계약

모듈마다 시작·진행·중지·정리 동작을 정한다. 페이지 이동과 크기 변경 시 리스너·GPU 자원·타임라인을 해제한다. 화면 밖 또는 비활성 탭에서는 계산을 멈추고 복귀 시 현재 진행도에서 복원한다. 무거운 장면은 동적으로 불러오며 핵심 문장과 상담 버튼은 먼저 사용할 수 있게 한다.

### 성능 예산의 초기 제안

초기 화면의 필수 전송량은 1.5MB 이내를 목표로 하고 3D 코드·추가 영상은 이후 분리한다. 동시에 활성화하는 무거운 3D 장면은 1개로 제한하는 안부터 검증한다. 효과는 측정 대상 PC에서 60fps, 저사양 모바일에서는 안정적인 간소화 표현을 목표로 한다. 이는 측정 결과나 납품 보장이 아닌 시편의 판단 기준이다.

대표 장면 하나를 만들어 재질, 글라스 가독성, 모바일 열·배터리 부담과 다운로드 비용을 비교한다. 기준을 넘으면 빛·해상도·후처리를 조정한다. 영상을 미리 렌더링할지 실시간으로 그릴지도 장면별로 정한다.

HyperFrames 공식 저장소는 CLI의 Node.js 22+와 FFmpeg 요구를 명시한다. Windows에서의 설치·렌더·코덱 검증은 다음 기술 시편 단계의 작업이다. 공식 문서 확인을 로컬 실행 성공으로 표현하지 않는다. [T06]

## 12 90점 목표와 Playwright 검수 루프

‘90점’은 내부 품질 목표다. 수상·Awwwards 선정 가능성을 점수로 보장하지 않는다. 기능 검사와 디자인 평가는 따로 기록하며, 자동 테스트가 통과해도 시각적 지적이 남아 있으면 완료 처리하지 않는다.

| 디자인 평가 항목 | 배점 | 검토할 증거 |
|---|---|---|
| 회사 고유의 시각 정체성 | 25 | 로고·실제 작업에서 도출한 장면, 템플릿 유사성 |
| 타이포그래피·편집·화면 구성 | 20 | PC·모바일 주요 장면과 실제 문장 길이 |
| 모션의 완성도와 일관성 | 20 | 진입·전환·정지·역방향 재생 영상 |
| 마케팅 설득력과 실제 근거 | 20 | 서비스→사례→상담 경로, 실제 산출물 |
| 조작성·가독성·성능 | 15 | 탐색, 키보드·터치, 느린 기기 대체 |

### 기능 검수의 대상

Playwright는 Chromium·Firefox·WebKit의 주요 PC·모바일 크기를 확인한다. 메뉴·CTA·필터·목록 복귀·직접 URL 진입, 깨진 이미지·가로 넘침·콘솔 오류를 검사한다. 문의는 오류·제출 중·성공·실패·재시도·첨부·중복을 확인하고 실제 수신 환경 검증은 별도 증거로 남긴다.

모션은 시작·중간·끝 캡처와 재생 영상을 함께 본다. 스크롤 역방향, 화면 크기 변경, 모션 감소를 실행 중 켜기, GPU 실패, 비활성 탭 복귀를 점검한다. 결정적 시간·진행도 테스트 훅을 제안해 매번 다른 프레임만 비교하는 문제를 줄인다. 실제 Android·iPhone 검수는 브라우저 엔진 테스트와 별도다.

### 수정의 반복 단위

요구 추적 → 정적 시편 → 모션 시편 → PC·모바일 캡처 → 결함 목록 → 수정 → 해당 결함 재검증의 순서로 반복한다. 블로커가 없고 내부 90점 기준과 사용자의 시각 피드백을 충족할 때 다음 단계로 간다. 라이브러리나 장식의 개수를 늘리는 방식으로 반복하지 않는다.

이번 확인은 R01 참고파일의 Chromium 3가지 조건과 기획 문서 검수다. 2026년 10월 2일의 기존 346개 로컬 검사는 새 구조의 검증 결과로 재사용하지 않는다. 실사이트 교체·메일 수신·SNS 게시 검증도 이번 범위에 포함되지 않는다.

### 범위와 일정에 영향을 주는 미정 항목

전체 영문판 포함 여부, 사례 편집량, 모션 원본 제작량, 문의 전달과 CMS 제품, 호스팅 조건이 남아 있다. 이 항목을 보지 않고 고정 일정·비용을 확정하지 않는다. 자료 확보를 기다리는 동안 트리와 디자인시스템 시편은 진행할 수 있다.

SNS는 같은 로고·글자·색·모션 규칙을 공유한다. 홈페이지의 실제 사례가 정리된 뒤 프로젝트 소개와 업무 설명을 채널 형식으로 편집한다. 언론 배포와 외부 게시 자체는 별도의 실행 작업이다.
