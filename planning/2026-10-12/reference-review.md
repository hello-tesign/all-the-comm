## 1. 판단 요약

## 6. 남길 것과 제거·재구성할 것

### 재활용할 가치가 있는 요소

- **회사 존재 이유**: “홍보 담당자가 없거나 인력이 부족한 기업의 마케팅 조력”은 누구에게 왜 필요한지 구체적이다(L204–205). About 본문과 상담 안내의 실제 고객 상황으로 활용한다.
- **과제→판단→산출물**: 사례의 전략 설명 구조(L315–318 등)는 결과 이미지에 맥락을 준다. 정식 상세의 과제→전략→실행→결과로 확장하되, 증빙 없는 결과는 만들어 넣지 않는다.
- **관심 서비스 반응**: hover뿐 아니라 focus/click도 처리한다(L420). 설명은 숨겨진 데스크톱 패널에만 두지 않고 모바일에서도 같은 내용을 접근 가능하게 만든다.
- **속도를 고려한 모션 구조**: canvas해상도 상한, reduced 설정, passive scroll/wheel, 한 번만 관찰하는 reveal 등은 좋은 출발점이다. 아래 결함을 고쳐 재사용한다.
- **기본 접근성 요소**: 입력 라벨·autocomplete, status영역, 이미지 alt, 장식 canvas aria-hidden, 본문바로가기 의도를 유지한다(L168, L194, L321/334/347, L365–381).

### 디자인 판단상 버리거나 크게 바꿀 요소

- 서비스·기준·업무과정을 선과 숫자로 반복하는 구성(L94–112, L224–258, L272–275). **사용자가 거절한 보고서형 서비스표와 같은 계열**이다. 콘텐츠의 중요도와 실제 산출물의 형태에 따라 구성을 달리한다.
- `SIGNAL`, 좌표, 무작위 문자해독, 원·선·숫자·영문코드의 중첩(L185, L195–197, L207–210, L427–430). 브랜드의 실제 자산·성과와 연관이 약한 장식이다. 로고의 선형 구조를 사용하더라도 하나의 모티프로 제한한다.
- 중앙 원과 연결선으로 팀을 묶은 도식(L113–115, L287–295). 조직도처럼 보이지만 실제 조직 증빙은 없다. 역할·책임·클라이언트 접점을 설명하는 편집 구성으로 바꾼다.
- 카드 모서리 한쪽을 자른 패널과 의미 없는 원형 장식(L99–101), 사례 위의 반복 영문 문구·선·원(L128, L321 등). 실제 작업 이미지의 식별과 가독성을 해칠 수 있다.
- 다수 섹션의 비슷한 큰 추상적 문장(“흐름으로 증명”, “판단의 과정”)과 작은 영문 보조라벨. 핵심은 매력적인 제목이 아니라 회사가 실제 맡을 일, 접근법, 증거다. 실제 고객 과제와 산출물을 문장 중심에 둔다.
- **글라스 카드 시안은 아니다**. blur가 있는 것은 헤더(L55)이며 서비스 패널은 불투명 배경(L99)이다. 사용자의 최근 글라스·아이콘 요구를 충족하는 참고로 오인하지 않는다.

이 절은 미적 판단이며 코드가 AI로 생성됐다는 출처 판정이 아니다. 디자인에 대한 판단과 기능상 결함은 분리한다.

| 중간 | reduced-motion 값은 초기 한 번만 읽고 설정변경에 응답하지 않음(L400–401). Desktop reduced에서도 L455의 `!compact` 조건으로 canvas 스크롤 redraw가 가능. | reduced조건 통일, 미디어쿼리 change 처리, 정지된 대표 프레임 유지 |

| 중간 | clipboard가 없는 환경에서는 `navigator.clipboard.writeText` 접근 자체가 실패할 수 있고 fallback도 반환값 없이 성공 안내(L462) | API지원과 결과 확인, 실패 시 직접 선택·복사 안내 |

서비스 설명에 `textContent`를 쓰는 것은 주입 방어상 좋은 선택이다. 문제는 문자열 삽입 자체가 아니라 제목을 애니메이션하는 방식과 컨트롤 의미·노출 범위다.

## 8. 파일 의존성과 자산 상태

L321 `assets/case-health.jpg`, L334 `assets/case-food.jpg`, L347 `assets/case-tech.jpg`를 참조한다. 수신 `index.html` 기준으로 다음 경로의 존재를 확인했고 **3개 모두 없음**이었다.

```text
C:\Users\home\Downloads\assets\case-health.jpg   없음
C:\Users\home\Downloads\assets\case-food.jpg     없음
C:\Users\home\Downloads\assets\case-tech.jpg     없음
```

다른 위치에 같은 이름이 있는지 무차별 검색하지 않았다. 이 수신 파일만으로는 사례 비주얼까지 재현할 수 없다. 해당 그림을 임의의 스톡 이미지로 채워 실제 회사 프로젝트처럼 보이게 해서는 안 된다. 코드 자체도 L308에서 가상사례임을 명시한다.

로고 AI는 별도 자산 분석에서 확인한 실제 원본을 후속 적용해야 한다. 참고 HTML은 공식 로고 파일을 참조하지 않는다. 또한 외부 폰트·영상·지도·SNS SDK가 없으므로 이들을 이미 연결했다고 간주해서는 안 된다.

## 9. 먼저 확정할 권장 페이지 트리

아래는 S03 정식 범위에서 도출한 **기획 제안**이다. 원본 HTML의 현재 구조가 아니다.

```text
공개 사이트
├─ /                      메인
│  ├─ 핵심메시지 + 상담/프로젝트 CTA
│  ├─ 서비스 요약 8개
│  ├─ 대표 실제 사례 3–6건
│  ├─ 4단계 업무과정 요약
│  ├─ 회사 강점·기준 요약
│  └─ 상담 안내
├─ /about/                ABOUT US: 회사소개 → 업무기준5 → 비전
├─ /process/              OUR PROCESS: 분석 → 전략 → 실행 → 보고·개선
├─ /team/                 TEAM: 9개 수행 역할·협업 책임
├─ /works/                WORKS: 서비스10 → 필터·사례목록
│  └─ /works/{slug}/      기본정보 → 과제 → 전략 → 실행 → 결과 → 작업물
├─ /contact/              CONTACT: 안내 → 실제 문의폼 → 연락처·주소
├─ /privacy/              개인정보처리방침
└─ /404.html              없는 주소 안내

관리 영역 — 공개 사이트와 분리
├─ 로그인
├─ 사례: 목록 / 등록 / 수정 / 미리보기 / 공개상태 / 노출순서
├─ 서비스 분류: 사례별 복수 지정, IT·언론홍보 포함
└─ 문의: 선택한 수신방식에 따라 조회·처리 또는 지정 메일 전달
```

메인의 8개: 전략·브랜딩 / 디지털 마케팅 / 콘텐츠·디자인·영상(통합 표기 제안) / 미디어·오프라인 광고 / 인플루언서 마케팅 / 병원 마케팅 / IT 솔루션 지원 / 언론홍보.

WORKS의 10개: 전략·브랜딩 / 디지털 마케팅 / 콘텐츠·디자인 / 영상 제작 / 미디어·오프라인 광고 / 인플루언서 마케팅 / 병원 마케팅 / 사업·글로벌 컨설팅 / IT 솔루션 지원 / 언론홍보.

TEAM의 9개: 전략·마케팅 / 디지털 / 콘텐츠 / 디자인 / 영상 / 미디어 광고 / 인플루언서 / IT 솔루션 / 언론홍보. 이는 역할 표현이며 실제 고용형태·상설부서 수를 뜻하지 않는다.

2언어가 별도 확정되면 공개 트리만 언어별로 대응시키며, 관리 데이터에는 언어별 제목·본문·메타정보와 공통 서비스 식별자를 둔다. 한국어와 영어의 사례 수가 다른 경우 빈 페이지나 자동 번역된 허위 정보를 만들지 않고 공개정책을 정한다.

## 10. 제작 인계 순서와 완료 기준

1. **구조·자료표 확정**: S03을 기준으로 8/10/9,5기준,4과정 일치. 참고 HTML의 가상사례·중간본 분류를 별도 표시한다.
2. **콘텐츠 모델 정의**: 회사정보·서비스·역할·프로젝트·문의. 서비스는 공통 식별자로 메인/WORKS/문의폼에 연결한다. 고객 공개 허락과 결과 근거 필드를 둔다.
3. **디자인시스템 조정**: 실제 로고·기본색·한글 서체·모션 강도·화면 간격을 결정. 보고서형 반복 리스트와 장식 문구를 제거한 PC/모바일 핵심 화면을 먼저 만든다.
4. **기능 명세**: 관리자 사례 운영과 문의 수신방식을 구체화. 초안복사 시안과 실제 접수를 혼동하지 않는다.
5. **실제 자료로 시안 검토**: 이미지3~6건, 서비스 증빙, 역할 설명. 본문과 모션을 같은 중요도로 보지 말고 먼저 읽히는 정보와 문의 경로를 확보한다.
6. **Playwright 검수 설계**: 각 메뉴·상세 경로, 320–1920 폭, 키보드·Escape·초점, reduced-motion·no-JS, 언어별 링크(채택 시), 폼 성공/실패/중복/첨부/실수신, 관리자 등록·수정·정렬·공개, 누락이미지·오류·옛주소 이동을 확인한다.

현재 참고 HTML을 통과한 완성품으로 판정하지 않는다. 이번 결과는 소스 분석과 정식 요구사항으로의 인계안이며, 실제 렌더링·접수·운영 검수는 후속 구현에서 수행해야 한다.
