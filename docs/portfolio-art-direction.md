# 실제 화면을 중심으로 한 포트폴리오 연출안

검토 범위: 국문 WORKS와 공통 프로젝트 마크업. 2026-10-12. 아래 본문은 구현 전 편집 제안으로 보존한다. 이후 실제 캡처 5종과 6개 사례, 원본 확대 보기, 프레임 전개 모션을 반영했으며 최종 구현 기준은 `design-system/MASTER.md`, 결과는 `qa/HANDOFF.md`의 후속 반영 절을 따른다.

## 현재 화면의 문제

현재 WORKS는 제공 서비스 무대 다음에 자사 프로젝트 한 개를 큰 조감 목업으로 보여준다. 브랜드 표현의 출발점으로는 적절하지만, 4~6개의 사이트와 SaaS를 더할 때 같은 목업을 반복하면 실제 제작 내용보다 포장이 먼저 보인다.

현재 `.project-image-real`은 데스크톱 높이 540px / 모바일 330px에 `object-fit:cover`를 사용한다. 긴 캡처를 그대로 넣으면 화면 중앙만 잘리거나 중요한 상단 메뉴가 사라질 수 있다. `src/motion.js`의 `.project-visual img` 대상 확대·이동도 실제 UI 캡처에는 자동 적용하지 않는 편이 좋다. 어떤 페이지의 어떤 부분인지 먼저 읽혀야 한다.

`projectMarkup()`은 API를 받을 때 카드 전체를 다시 만든다. 정적 HTML에만 프로젝트 분류나 새 구도를 넣으면 접속 후 사라진다. 목록 필터, 더 보기, 상세 페이지가 같은 표시 규칙과 출처 정보를 사용해야 한다.

## 추천 편집 구성

실제 이름과 화면을 확인한 뒤 아래 자리에 배정한다. 현재 확인되지 않은 프로젝트 이름, 수행 범위, 고객 관계를 미리 채우지 않는다.

```text
PROJECTS
짧은 설명 + 수행 분야 필터

┌──────────────────────────────────────────────────────┐
│ 01 대표 작업 / 실제 사이트의 가장 명확한 첫 화면     │
│ 가로 전체 · 16:10 · 화면의 비율과 색을 그대로 유지   │
└──────────────────────────────────────────────────────┘
분류 / 프로젝트명                         실제 수행 범위

┌─────────────────────────┐  ┌─────────────────────────┐
│ 02 커머스·브랜드        │  │ 03 SaaS·업무 도구       │
│ 16:10 / 서비스 첫 장면  │  │ 4:3 / 핵심 작업 영역    │
└─────────────────────────┘  │ 조작부를 읽을 수 있게   │
분류 / 이름                 └─────────────────────────┘
                             분류 / 이름

┌─────────────────────────┐  ┌─────────────────────────┐
│ 04 콘텐츠·다국어 웹    │  │ 05 별도 콘셉트 작업     │
│ 4:3 / 콘텐츠 편집 장면 │  │ 16:10 / 콘셉트 표시     │
└─────────────────────────┘  └─────────────────────────┘
분류 / 이름                 분류 / 이름

06 올더 자사 리뉴얼 / 웹과 브랜드 모션
실제 자사 화면 + 선택 재생 가능한 영상
```

전체를 자동 masonry로 만들지 않는다. 데스크톱 12열에서 첫 프로젝트 12열, 이후 각 6열을 사용한다. 카드 사이 32px, 한 행 아래 다음 행까지 64~80px을 출발점으로 한다. 비율 차이는 프로젝트 내용에 의해 정하고, 홀수·짝수라는 이유만으로 기울이거나 위치를 크게 어긋나게 하지 않는다.

4개만 충분하다면 콘셉트 작업을 억지로 넣지 않는다. 6개를 채우기 위한 유사 화면의 반복보다 서로 다른 제작 능력이 보이는 4개가 낫다. 홈에서는 대표 1개 + 서로 다른 성격의 2개만 보여주고, 나머지는 WORKS에서 이어서 본다.

## 캡처를 읽을 수 있게 만드는 규칙

| 대상 | 메인 이미지 | 상세에서 보여줄 것 | 피할 표현 |
|---|---|---|---|
| 브랜드·기업 웹 | 실제 첫 화면의 16:10 또는 16:9 캡처 | 다음 핵심 섹션 2~3개와 모바일 화면 | 전체 페이지를 한 장에 축소 |
| 커머스 | 상품·카테고리·구매 흐름 중 한 가지가 뚜렷한 화면 | 상품 선택·상세·구매 흐름의 실제 제작 범위 | 검증되지 않은 결제 완료·매출 암시 |
| SaaS | 핵심 작업 공간을 담은 4:3 캡처 | 입력→결과 등 확인 가능한 작업 흐름 | 장식용 차트와 가짜 성과 숫자 |
| 콘텐츠·다국어 | 편집과 정보 구조가 잘 보이는 실제 페이지 | 대표 본문, 검색·탐색, 실제 제공 언어 | 언어가 바뀌는 장면을 실적처럼 과장 |
| 콘셉트 스터디 | 콘셉트라는 표시가 붙은 완성 화면 | 과제 설정, 디자인 선택, 구현 여부 | 실제 고객·출시·성과인 듯한 서술 |

대표 카드의 실제 표시 폭이 1250~1400px라면 1440px 안팎의 원본 화면이 적절하다. 2열 카드의 표시 폭은 대략 600~680px이므로, 1440px 전체 화면을 무조건 축소하면 UI 본문 16px가 7~8px로 내려간다. SaaS 카드에서는 원본의 약 760~900px 폭에 해당하는 핵심 영역을 선택해 보여주고, 전체 화면은 상세에서 넓게 제공한다. 캡처 영역을 바꾸더라도 실제 화면에 존재하지 않는 UI를 합성하지 않는다.

스크린샷 배경과 별도 무대가 필요하면 해당 프로젝트의 실제 색 또는 차분한 중립색을 쓴다. 모든 프로젝트에 올더의 민트색 유리 배경을 씌우지 않는다. 가짜 노트북, 브라우저 신호등, 과도한 그림자, 비스듬한 디바이스 프레임은 기본 요소로 사용하지 않는다.

프로젝트 제목과 수행 범위는 이미지 안에 덧씌우지 않고 아래에 둔다. 이미지 안에 있는 실제 웹사이트 문장과 포트폴리오 제목이 겹치지 않아야 한다. 순수 이미지에는 장식적 아이콘을 추가하지 않는다.

## 움직임의 구체적인 역할

| 상황 | 제안 | 제약 |
|---|---|---|
| 목록 진입 | 카드가 화면에 들어올 때 전체가 18~24px 이동하며 650~800ms 동안 정착 | 들어오기 전까지 기본 내용은 보이는 상태 유지 |
| 마우스 올림·키보드 초점 | 프레임은 고정하고 캡처를 최대 1.02배 확대, 450ms | 실제 UI 상단을 자르지 않도록 여유 확보; 3D 기울기 없음 |
| SaaS 캡처 | 기본은 정지. 필요하면 두 상태를 사용자가 선택 | 자동 숫자 증가, 흔들림, 지속 패럴랙스 제외 |
| 긴 웹페이지 | 상세 화면에서 ‘다음 장면’으로 미리 정한 다음 구간까지 한 번 이동 | 500~700px 내 이동, 약 2.0~2.4초 후 정지; ‘처음으로’ 제공 |
| 프로젝트 상세 진입 | 선택 이미지가 상세 이미지로 이어지는 지원 브라우저의 View Transition | 지원하지 않으면 즉시 정상 링크 이동 |
| 모바일·모션 감소 | 정지 캡처와 정상 링크 | hover 의존 기능, 고정 스크롤 구간, 자동 이동 없음 |

긴 페이지 전체를 위아래로 왕복시키는 자동 애니메이션은 쓰지 않는다. 읽고 있는 UI가 계속 이동하면 실제 작업의 디테일을 볼 수 없다. 긴 페이지는 대표 장면 2~3개를 편집한 뒤 사용자가 넘기도록 하는 편이 효과적이다.

예상 인터랙션 순서: 정지 화면으로 식별 → 호버 시 아주 작은 확대 → 클릭하면 넓은 상세 화면 → 필요한 경우에만 다른 구간 또는 실제 사이트로 이동. 움직임은 이 순서를 강화해야 한다.

‘다음 장면’과 ‘프로젝트 보기’를 함께 두는 경우 버튼을 링크 내부에 중첩하지 않는다. 이미지 컨테이너 안의 별도 형제 요소로 만들고, Enter/Space·초점 표시·모션 감소를 각각 확인한다. 기본 목록에서는 별도 미리보기 버튼을 생략해도 된다.

## 출처와 수행 주체 표시

사용자가 포트폴리오 게재를 승인한 것과 ‘올더커뮤니케이션의 고객 수주 실적’이라는 사실은 구분해야 한다. 독자가 이미지가 누구의 어떤 작업인지 한 번에 알 수 있도록 카드 제목 바로 위에 분류를 항상 노출한다. 푸터의 작은 설명으로만 처리하지 않는다.

| 분류 | 카드의 표기 예 | 상세의 첫 문장 | 상세 정보의 항목명 |
|---|---|---|---|
| 올더 자체 제작물 | 자사 프로젝트 · 2026 | 올더커뮤니케이션의 자사 홈페이지 리뉴얼입니다. | 프로젝트 / 수행 범위 / 연도 |
| 제작자가 만든 독립 사이트·제품 | 제작자 프로젝트 · 웹사이트 | 이 홈페이지 제작자가 별도로 진행한 프로젝트입니다. | 프로젝트 / 제작자 역할 / 공개 상태 |
| 제작자의 SaaS 제품 | 제작자 프로젝트 · SaaS | 제작자가 기획·구현한 제품의 실제 화면을 소개합니다. | 제품 / 제작 범위 / 화면 기준일 |
| 가상 제안·디자인 연구 | 콘셉트 스터디 · 미출시 | 역량 소개를 위해 구성한 가상 프로젝트입니다. | 가상 과제 / 디자인 범위 / 구현 여부 |
| 실제 올더 고객 프로젝트 | 고객 프로젝트 · 업종 | 확인된 고객 관계와 실제 수행 범위를 서술합니다. | 고객 / 수행 범위 / 기간 |

‘제작자 프로젝트’만으로 정확한 주체를 알기 어렵다면 상세 첫 문장에 실제 제작자명 또는 스튜디오명을 넣는다. 이름이 정해지기 전에는 임의의 회사명을 만들지 않는다. ‘제작자 프로젝트’를 ‘올더 제작’으로 줄이지 않는다.

현재 상세 페이지의 고정 `CLIENT`는 실제 고객이 없는 제작자 프로젝트·자사 제품·콘셉트에는 맞지 않는다. 위 표처럼 의미에 맞는 항목명으로 바꿔야 한다. 제목이 ‘만들어낸 장면들’이더라도 바로 옆 설명을 ‘제작자의 웹·제품 작업과 자사 프로젝트를 소개합니다’처럼 정확하게 쓰면 전체를 고객 실적으로 읽을 가능성이 줄어든다.

분류 표기는 데스크톱 12px, 모바일 11px 이상을 출발점으로 한다. 긴 설명이나 경고 배지를 쌓을 필요는 없다. 제목 위의 짧고 정확한 구분과 상세 첫 문장으로 충분하다.

확인되지 않은 고객명, 협업 관계, 출시 상태, 사용자 수, 매출, 전환율, 업무 성과는 추가하지 않는다. SaaS 화면의 예시 데이터는 필요하면 ‘데모 화면’이라고 표시한다. 계정명·이메일·고객 정보·접근 토큰이 캡처에 포함되지 않는지도 확인한다.

## 콘텐츠가 유지해야 할 최소 정보

```text
프로젝트 ID / 이름
분류: 자사 · 제작자 프로젝트 · 콘셉트 · 확인된 고객 프로젝트
제작 주체와 실제 수행 범위
공개 상태: 운영 중 · 개발 중 · 데모 · 콘셉트
원본 주소 또는 로컬 캡처 원본 경로
캡처 기준일 / 화면 유형 / 원본 뷰포트
표지 이미지 / 초점 위치 / 적정 표시 비율
상세 이미지와 설명
프로젝트 주소 / 게재 근거
성과 문장과 그 근거 — 없다면 비워 둠
```

이는 신규 관리 화면을 만들라는 요구가 아니라, 목록·API 응답·상세 페이지가 잃지 않아야 할 정보의 계약이다. 기존 프로젝트 스키마를 확장할 때 API의 필드 허용 목록과 관리자 저장 동작까지 같은 기준을 적용해야 한다.

## 통과 기준

- 국문 PC WORKS에서 서로 다른 실제 화면 4~6개가 식별된다.
- 첫 화면·목록·상세에서 프로젝트 분류가 일관된다.
- SaaS의 핵심 조작부를 읽을 수 있으며 긴 전체 화면이 작은 카드에 압축되지 않는다.
- 각 이미지의 초점이 원본과 맞고, 의미 있는 제목·메뉴·작업 영역을 잘라내지 않는다.
- 전체/서비스 필터와 더 보기 후에도 비율·출처·링크가 유지된다.
- 키보드 탐색과 모션 감소에서도 동일한 정보에 접근한다.
- 이미지를 늦게 로드해도 레이아웃이 흔들리지 않으며, 긴 영상은 초기 진입 시 자동 다운로드하지 않는다.
- 카드나 설명 어디에도 제작자 개인 작업을 올더 고객 수주·성과로 바꾸는 표현이 없다.

이 편집안은 실제 캡처가 들어오는 대로 프로젝트별 초점과 비율을 결정하기 위한 기준이다. 현재 한 개의 자사 목업만으로 완성도를 평가했던 화면과 달리, 최종 평가는 실제 이미지·카드 순서·상세 내용이 들어간 화면에서 수행해야 한다.
